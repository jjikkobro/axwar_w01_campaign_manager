# Aurora SCM 데모 영상 기획안

수정일: 2026-11-12 · 현재 구현 반영판 · GPT 연결 완료 사용자 확인 반영. 아래는 촬영 기획이며 전체 시연의 리허설 완료 보고가 아니다. 촬영용 격리 DB에서 실제 결과를 확인한 뒤 입력값·자막을 확정한다. 사용자 캠페인·원본 자료·보호 폴더는 수정하지 않는다.

## 전달할 메시지

“마케팅이 기획할 때부터 재고·보충량·비용·현금 제약을 확인합니다. 각 부서는 같은 근거를 검토하고, GPT는 위험·대안·질문 초안을 돕습니다. 조건이 바뀌면 검토와 담당 업무가 다시 연결되며, 최종 결정은 사람이 합니다.”

주요 변화는 부서 검토를 없애는 것이 아니라 반복 입력·근거 확인을 앞당기는 것이다. SCM·재무 검토와 승인권자의 명시적 결정을 유지한다. 모든 캠페인이 마케팅에서 승인권자로 자동 직행한다고 설명하지 않는다.

## 촬영 준비와 고정 조건

- 접속: 로컬 `http://127.0.0.1:8088`. 녹화는 운영·현재 사용자 DB가 아닌 별도 시연 DB로 실행한다.
- 가상기업 기준일은 2026-07-01, 현재 현금 전망은 2026-07-01~2026-09-28이다. 실제 촬영일의 사건 시각과 구분한다.
- 캠페인 기간이 범위 안이어도 집행비 예측 지급일이 이후이면 신청이 막힌다. 자동 예측 후 지급일을 반드시 확인한다. 지급일을 영상 편의를 위해 근거 없이 당겨 원본 관행처럼 설명하지 않는다.
- 정상 사례에서 9/21 지급 조건을 쓰면 ‘시연용 담당자 협의 가정’으로 명시하고 직접 입력한다. 원본에 확정된 조건 또는 GPT가 보장한 지급일이 아니다.
- 부서 전망과 원본 기반 재계산은 구분한다. 연체 회수·인플루언서 전속계약은 별도 검토 업무로 시연하지 않는다. 필요한 내부 현금 계산만 유지한다.
- 사용자가 GPT 연결을 완료했다고 확인했다. 이번 기획 수정 과정에서는 추가 유료 호출이나 키·설정 변경을 실행하지 않는다. 촬영 사례의 실제 요청·출력·반영 기록은 리허설로 확보한다.
- 모델·키 상태는 촬영 직전에 공개 설정 화면에서 확인한다. 이전 기록의 미연결 상태나 키 등록 여부만으로 실제 API 호출 성공을 단정하지 않는다.
- 관리자에서 API 키를 입력하는 구간은 녹화하지 않는다. 키를 브라우저 개발도구·터미널·영상에 노출하지 않는다. 모델명·연결 상태·프롬프트만 보여준다.
- 실제 GPT 호출 장면은 관리자의 연결 테스트와 해당 캠페인 초안 생성 리허설을 성공한 경우 촬영한다. API 호출은 비용이 발생할 수 있다. 실패하면 실패 상태를 표시하고 실제 운영 AI 시연은 미완료로 기록한다.
- A/B는 같은 초기 조건의 독립 분기다. A에서 전달한 발주를 B에서 아직 승인 전인 것처럼 되돌려 편집하지 않는다. C는 B의 반려 분기에서 이어간다.

3. 기간만 8/17~8/23으로 바꿔도 지급예정일이 12/24라면 여전히 차단됨을 짧게 보여준다.

증거: 차단 사유 / 신청 점검 / SCM 신규 건 미생성. 보조 자료로 [마케팅 사전 차단 검증](../verification/marketing/MARKETING_CASH_WINDOW_RESULTS.json)을 연결한다. 기존 진행 건을 소급 삭제·반려하는 기능은 아니다.

## 시나리오 A: 같은 근거가 기획부터 일정 기록까지 이어짐

### 입력 준비안

- 제목: `[시연 A] 색조 캠페인 공급 준비`.
- 기준일 7/1, 캠페인 8/17~8/23, SKU-3003 색조 아이팔레트부터 시작.
- 추가 수요는 자동 예측값과 출처를 먼저 확인한다. 직접 수정하면 값·단위·근거를 함께 기록한다.
- 집행비 지급예정일은 9/21의 시연용 협의 조건. 자동 초안과 다르면 담당자가 직접 수정하고 이유를 남긴다.
- 신규 발주가 타당한 시연 분기 예: 10,000EA × 참고 단가 16,800원 = 168,000,000원. MOQ·최신 단가·수량 필요성은 리허설에서 확인한다. 계산상 발주가 필요 없으면 단순히 발주 장면을 만들기 위해 이 값을 강제하지 않는다.
- 발주 필요 사례는 별도 수요 가정을 근거와 함께 준비한다. 발주일 7/1·판매가능일 8/12는 해당 SKU 리드타임 6주의 모의 조건이며 공급능력을 확인한 사실이 아니다. 모의 공급처 회신에서 별도로 확인한다.
- 캠페인 마케팅비 M, 조달비 P, 총 요청비 M+P를 영수증형 항목과 합계로 보여준다. 표본 마케팅비를 전사 현금에 임의 합산하지 않는다.
- 발주대금도 9/21 지급 조건을 사용하되 재무가 확인한다. 실제 계산상 평시 경로인지 확인한 뒤 촬영한다. 리허설 결과가 다르면 수치를 숨겨 평시 경로라고 설명하지 않는다.

| SCM 발주 | 승인된 제품·수량·금액을 불러와 모의 전달 기록 | 발주서 자동 채움, 승인 범위 유지, 다음 단계가 입고예정 회신 확인임을 확인 |
| SCM 회신 | 수량·판매가능일·지급일의 모의 회신 기록 | 실제 발주·은행 지급 아님. 일정 변경 여부 재판정, 후속 단계 갱신 |
| 마케팅 일정 | 확인된 일정·남은 업무 확인 후 기록 정리 | 입고·발주 지급 일정이 SCM 기록에서 연결됨. 종료는 기록 완료이며 실제 판매 성공 아님 |

정기 보충만 필요한 분기는 신규 발주서를 억지로 만들지 않는다. 재고·기존 공급 확인 후 실제 서버가 안내하는 후속 화면을 따른다. 발주서까지 보여줄 주 사례가 필요하면 추가 발주가 타당한 별도 A 분기를 준비한다.

GPT 출력은 고정 대본으로 미리 정답처럼 표시하지 않는다. 예상 형식은 `[요약] → [위험] → [대안] → [확인 질문] → [근거]`의 한국어 개조식이다. 생성 후 입력을 바꾸면 이전 초안 반영이 차단되는 장면을 짧게 삽입할 수 있다. 프롬프트는 입력 문서의 지시보다 고정된 승인 경계를 우선한다.

증거: 캠페인 ID / SKU / 비용 항목 / 마케팅 예측 지급일 / 부서 코멘트 / GPT 초안 생성 이력 / 사람 반영·인계 / 승인 / 발주 / 회신 / 마케팅 일정.

## 시나리오 B: 지급 조건 변경이 CEO 상신으로 이어짐

A와 동일한 초기 자료·수요·금액을 가진 승인 전 별도 분기에서 시작한다. 추가발주 검토안을 대상으로 하며 원본 SPO의 기존 약정을 신규로 재라우팅하는 사례로 만들지 않는다.

1. 신규 발주안의 9/21 지급 조건과 평시 SCM 승인 경로를 보여준다. 동일 분기의 마케팅비 지급 조건은 고정한다.
2. 공급처가 7/21 선지급을 요청했다는 모의 사건을 입력한다. 재무에서 SCM으로 조정 요청을 남긴다.
3. SCM이 제품·수량·단가는 유지하고 신규 발주안 지급일만 7/21로 바꿔 재인계한다. 전달된 발주를 직접 수정하는 사례가 아니다.
4. 이전 검토·승인 근거는 이력으로 남고 대기 건은 새 조건으로 재검토되어야 한다.
5. 같은 재무 시나리오에서 신규 유출일이 30억원 하회구간에 들어가면 CEO/이사회로 경로가 바뀌는 것을 보여준다. 리허설에서 시나리오·하회구간·신규 유출액을 함께 고정한다.
6. GPT에 최신 근거로 다시 검토를 요청해 위험·지급 분할 또는 감량 등 대안·확인 질문을 받는다. 대안은 제안이며 협의 완료·자금 확보로 간주하지 않는다.
7. 재무 의견·대안을 붙여 사람이 상신하고 CEO 화면에서 앞 단계 코멘트를 확인한다.

필수 확장 E1은 일별 현금 재전망을 신규 약정 결재권한·재검토 상태에 연결한 것이다. 다른 부서 영향은 마케팅 실행을 위한 SCM 조달 조건이 재무의 단독 현금 제한에 걸려 승인권자·대안·담당 업무가 바뀌는 점이다.

확장 없는 경우와의 비교는 공식 전망과 원본 재계산을 나란히 보여준다. 공식 주차 최저 약 54.69억원과 보수적 원본 재계산 약 14.68억원은 서로 다른 성격의 자료다. 공식 전망만 믿은 가상의 경로는 ‘반사실 비교’라고 표시하고 실제 승인에 사용하지 않는다. 신규 발주 반영 후 최저값은 화면 결과를 별도로 기록한다.

## GPT 검토를 보고 사람이 판단을 수정하는 핵심 장면

이 장면은 B의 조정 요청 시점에 실제로 촬영하고 편집상 별도 확대 장면으로 배치한다. GPT 호출만 보여주거나 생성 문장을 그대로 붙여넣는 것으로 끝내지 않는다.

1. **검토 전 판단:** 재무 담당자가 화면에서 선택한 기존 의견과 판단 사유를 보여준다. 예: 지급 조건의 위험을 충분히 반영하지 않은 ‘승인’ 의견 초안. 원본의 승인권한을 잘못 바꾼 상태를 준비하지 않는다. 아직 저장·승인하지 않은 담당자 초안이다.
2. **AI 입력 확인:** 해당 캠페인의 금액·7/21 신규 발주 유출·하회구간·SCM 의견·자료 버전을 근거로 GPT 검토를 실행한다. 전체 키·원천 거래를 영상에 노출하지 않는다.
3. **AI 출력 검증:** 위험·대안·확인 질문 중 실제 데이터와 맞는 항목을 담당자가 선택한다. 지급 분할·일자 변경 제안은 협의 후보일 뿐이며, 현금 부족을 해소한 사실로 인정하지 않는다.
4. **사람의 판단 수정:** 담당자가 ‘승인’ 초안을 ‘조건부 검토/보완 필요’ 방향으로 바꾸고, 사유를 직접 작성한다. 예: “7/21 신규 유출이 하회구간에 포함되어 바로 진행하기보다 공급처 지급 조건 재협의를 먼저 요청합니다.” GPT의 의견 반영 버튼은 문장 복사이며 승인 선택·수량·지급일을 자동 변경하지 않으므로 해당 필드는 사람이 수정한다.
5. **실제 후속 행동:** 다른 부서 조정 요청으로 SCM에 지급 조건 재검토를 전달한다. 요청 내용·대상 부서·처리 단계가 저장되고 SCM 목록에 도착하는 것까지 보여준다. 기존 B의 조정 요청 장면을 재사용하며 별도 가공된 사건으로 중복 설명하지 않는다.
6. **재검토:** SCM 회신·수정안으로 재무가 다시 계산하고 재생성한 GPT 초안을 검토한다. 변경된 지급일에도 결재선이 유지되면 유지 이유를, 바뀌면 변경 근거를 보여준다. CEO 상신 자체와 실제 승인은 분리한다.

반드시 남길 비교는 `검토 전 사람 의견 → GPT 제안·참조 근거 → 채택/기각한 내용 → 수정된 사람 의견·사유 → 요청·업무 상태`다. AI가 올바른 권한을 뒤집었다고 표현하지 않는다. 근거가 부족하거나 GPT 제안이 부적절하면 해당 제안을 기각하고 이유를 기록하는 것이 정상 동작이다. 모델이 원하는 문구를 내도록 결론을 강요하거나 실제로 없던 채택을 편집하지 않는다. 구체적인 의견 변경이 가능한 사례는 리허설에서 선정한다.

## 시나리오 C: 반려·조정 요청 후 마케팅이 직접 재작성

B의 CEO 승인 요청에서 반려 분기로 이어간다.

1. CEO가 자금 대안 미확보를 사유로 반려하고 기록한다. 승인 버튼만 눌러 지급 제약이 해소되는 연출을 하지 않는다.
2. 조정 요청을 사용할 수 있는 승인·발주 전 단계에서 ‘기안 변경 요청’을 마케팅으로 전달한다. 사유 예: “선지급 부담을 낮출 수 있도록 수량·상품 구성·시기를 다시 검토해 주세요.” 반려 후 버튼이 제한되면 서버가 제공하는 보류·재검토 경로를 따르고 실제 기록을 남긴다.
3. 우측 상단 역할 변경 버튼으로 마케팅으로 전환한다. 이것은 시연용 역할 선택이며 실제 로그인 사용자 인증을 구현한 증거가 아니다.
4. 마케팅의 처리할 캠페인에 요청과 근거가 도착한 것을 확인한다. 자동 연결·자동 수정 없이 기존 기안을 열어 직접 수정한다.
5. 수요·구성·예산을 재계산한다. 일정이나 지급예정일을 바꾸면 마케팅 전망 범위 검증도 다시 적용된다.
6. SCM에 재신청하고 조정 요청 완료·다음 담당 단계·이전 반려 이력을 보여준다. 이전 승인을 재사용하지 않는다.

변경 전후 비교는 요청 수량·조달비·지급일·결재선·담당 단계·기안 버전을 같은 표에 기록한다. 결론이 유지되면 유지된 이유도 화면에서 확인한다.

## 시나리오 E: 관리자가 프롬프트·산식·자료를 개선하고 재검증

마지막 장면은 ‘코드 수정 없이 업무 모델을 관리하고, 바뀐 근거가 현업의 다음 판단에 반영된다’를 보여준다. 발주 전달·종료 전 별도 `[시연 E]` 캠페인과 격리 DB를 사용한다. A의 완료 건을 다시 열린 건처럼 보이게 하지 않는다. 세 변경은 하나씩 적용하고 매번 전후 값을 기록한다. 효과를 구분할 수 없다면 같은 초기 상태의 독립 분기로 나눈다.

### E1. 프롬프트 수정 → 실제 새 검토 결과 비교

- 위치: 시스템 관리자 → AI 프롬프트 설정. 재무 단계 프롬프트는 재무 역할로, SCM 단계는 SCM 역할로 편집한다.
- 수정 전: 같은 사건의 개조식 출력·프롬프트 버전·모델을 캡처한다.
- 추가 문구 예: “각 위험에 관련 SKU 또는 지급일·금액과 출처를 붙여라. 대안별로 확인할 담당 부서와 다음 행동을 한 줄로 써라. 기존 약정으로 발생한 하회와 이번 신규 유출의 영향을 구분하라. 자료가 없으면 미확인이라고 써라.”
- 수정자·사유·근거를 입력해 저장한다. 한국어 개조식과 고정된 Human-led·승인권한 경계는 유지한다.
- 같은 캠페인·자료·산식·모델을 유지한 채 ‘다시 검토’를 실행한다. 프롬프트 저장만으로 기존 GPT 출력이 소급 수정되는 것이 아니다.
- 새 출력의 근거 표시·확인 질문이 어떻게 달라졌는지 담당자가 검토하고 필요한 문장만 반영한다. 프롬프트 버전과 새 생성 이력을 함께 보여준다.
- 프롬프트만 바꿨다면 수량·현금 계산·규칙 결재선은 같아야 한다. 문장 변화는 모델의 비결정성도 있으므로 한 번의 전후 출력만으로 품질 향상률을 주장하지 않는다.

### E2. 계산식 수정 → 시험·변경 영향·명시적 적용

- 위치: 같은 관리자 페이지의 계산식 설정, SCM 역할. 대상은 편집 가능한 `리드타임 반영 발주점`이다.
- 기본식: `weekly * (lead_weeks + review_weeks + safety_weeks)`.
- 변경 예: `weekly * (lead_weeks + review_weeks + safety_weeks + 1)`. ‘공급 불확실성에 대비한 1주 추가 여유’라는 **시연용 내부 관리 가정**으로 사유·근거를 기록한다. 원본 안전재고 규정이 바뀐 것으로 설명하지 않는다.
- 시험 입력: weekly=1,000, lead_weeks=6, review_weeks=1, safety_weeks=4. 기본 발주점 11,000EA → 변경안 12,000EA를 확인한다. 이는 시험값이며 실제 회사의 발주량·발주일이 아니다.
- ‘변경 영향 확인’으로 E 캠페인의 발주 시점·계산값을 비교한 뒤 ‘검증한 산식 적용’을 누른다. 모델 식 변경이 발주량 변화로 직결된다고 미리 단정하지 않는다. 변경이 없는 경우에도 해당 조건과 이유를 보여준다.
- 마케팅 예상안과 SCM 대조가 같은 공통 산식 버전을 읽는지 다시 확인한다. 기존 초안·재무 확정·검토/승인의 현재 유효성과 재검토 단계도 확인한다. 저장된 승인 이력은 삭제하지 않는다.
- 일별 현금 수지·30억원 기준·승인권한·PO 연결 AP 중복 차감 방지는 고정 규칙이다. 이런 규칙을 변경해 통과시키는 장면은 넣지 않는다.

### E3. 기준자료 사본 수정 → 재계산·오래된 검토 재확인

- 위치: 관리자 → 기준자료 → SCM 재고의 자료별 업데이트. 원본 `04_원본데이터` 파일을 편집하지 않고 서버의 시연 DB 사본을 갱신한다.
- 입력 예: E의 대상 SKU 현재고를 기존 값에서 500EA 낮춘다. 실제 자료가 충분히 있는 SKU를 리허설에서 선택하며 음수 재고는 만들지 않는다. 이유는 “시연용 실사 수량 정정”이고, 증빙은 실제 회사 증빙처럼 꾸미지 않는 **모의 담당자 회신**으로 구분한다.
- 현재 자료 내려받기/불러오기 → 대상 1행 수정 → 서버 검증 → 변경 행 수 확인 → 수정자·사유·출처를 기록하고 저장한다. 다른 거래·SKU·리드타임을 동시에 바꾸지 않는다.
- 같은 E 캠페인을 다시 열어 자료 버전·기초 재고·예상 재고·보충 검토의 변화를 보여준다. 기존 판단이 계속 유효하다고 방치되지 않고 재확인이 필요한지도 확인한다.
- GPT 검토를 새 근거로 재생성하고 담당자가 판단을 유지하거나 수정한 이유를 기록한다. 자료 갱신만으로 새 발주나 사람 승인이 만들어지지는 않는다.
- 파일 정정과 실제 공급처 회신 입력은 서로 다른 업무다. 이 장면의 정정값은 합성된 시연 입력이며 실제 재고 감소를 확인한 사실이 아니다.

### 마지막 비교 화면

| 바꾼 것 | 즉시 바뀌는 대상 | 그대로 지켜야 할 경계 | 증거 |
|---|---|---|---|
| 프롬프트 | 다음 GPT 요청의 지침·새 초안 | 계산값·규칙 결재선·승인 상태 자동 변경 금지 | 프롬프트 버전·전후 출력·사람 채택 |
| 산식 | 새 버전 계산·변경 영향·재검토 필요성 | 고정 현금/권한 규정·이전 승인 기록 보존 | 시험값·미리보기·적용 이벤트·화면별 버전 |
| 기준자료 | 해당 SKU 계산 근거·전망·검토 유효성 | 원본 파일·출처 구분·기록 보존 | 수정 전후 행·자료 버전·재검토·재생성 |

되돌리기까지 시연한다면 기존 식·자료를 다시 영향 확인·검증 후 명시적으로 적용한다. 복원은 또 하나의 변경 이력이며 과거 승인을 되살리는 행동이 아니다. 프롬프트·산식·데이터를 한꺼번에 바꾸고 어떤 변경이 결과를 바꿨는지 알 수 없는 장면으로 끝내지 않는다.

# ② SCM 화면 컨펌 반영·실행 기록

2026-11-10 · 사용자 '진행해' 컨펌 후 구현. 첨부 시안의 페이지 구성과 현재 캠페인 단계 플로우를 유지했다.

## 적용 범위

②의 업무 제목·개요·재고/입고표·발주안·판단/결정·검토 규정 섹션 안에서 내용을 교체했다. 독자 대시보드나 별도 모달형 SCM 페이지를 만들지 않았다. 확인되지 않은 값은 미확인으로 표시하고, SCM 담당자가 명시적으로 인계할 때만 ③ 작업을 만든다.

| 영역 | 실제 반영 |
|---|---|
| 기안 연결 | 현재 캠페인의 선택 SKU·수요 단위·적용기간·근거·기안 버전 조회 |
| 공급 대조 | 완료 4주 평균·현재고·원본 커버와 재계산·캠페인 기간별 재고·첫 부족 표시 |
| 기존 발주 | SKU별 PO·수량·대금·발주/지급일 대조. 보존 원본과 현재 DB 수정값·출처를 구분 |
| 공급 회신 | 잔여 수량·입고일·검수 후 판매가능일·기록자·근거·모의/부서 주장 저장. 최신 기존 PO 회신만 적용 |
| 중복 방지 | 운송 중을 확인 입고에 다시 더하지 않음. 미승인 신규 조달안·입고 가정은 실제 공급량에 반영하지 않음 |
| 권고 발주량 | max(목표량−현재고−운송 중, 0), 양수면 MOQ 최소량 적용. 목표 미입력은 미확정. MOQ 배수 주문을 강제하지 않음 |
| 발주 검토 초안 | 기존 발주 확인/변경·신규 발주 검토·추가 없음·판단 대기 구분. 목표·요청 수량·과거 역산 단가·추정액·새 발주/입고 가정·요청 지급일 분리 |
| 정보 부족 | 추가 확인 대기와 부서 요청·회신·근거 기록. 미확인 회신으로 공급량 추가/PO 요청 완료 처리 금지. 확인 회신이 미확인으로 바뀌면 요청 재개 |
| 사람 판단 | 처리 방향과 SKU별 공급 의견·사유·근거·대안을 저장. 공급 불가 의견은 승인권자의 정식 반려가 아님 |
| 재무 인계 | 유효 기안·자료 버전·SCM 의견·조달안·원본 PO·근거 첨부 ID를 포함한 미승인 패킷과 재무 확인 작업 저장 |
| 변경 | 수요·발주·공급 회신·SCM 근거가 바뀌면 이전 인계 무효화와 재검토. 이전 기록은 사건 이력에 보존 |
| 통제 | SCM 역할 검증·서버 입력 제한·동시 버전 충돌·명령 중복 방지. 승인·발주·지급을 실행하지 않음 |

계산·확인 작업은 참가자 추가 설계/내부 통제로 구분한다. 실제 AI 호출이 없는 계산을 AI 결과로 표시하지 않는다.

## 실행 결과

기존 39개와 SCM 14개를 합쳐 **53개 단위·회귀 테스트 통과**. [로그](../verification/screen-reviews/02-scm-tests.txt).

별도 로컬 PostgreSQL DB `w01_scm_test`와 포트 8085에서 다음 시나리오를 실제 저장·재조회했다. 공급자·마케팅 입력은 모의이며 외부로 메시지를 보내지 않았다.

| 시나리오 | 입력·상태 변화 | 검증 |
|---|---|---|
| 정상 | SKU-2002, 7/13~19 추가 1,000EA. SCM 저장 → ② 유지 → 담당자 인계 → ③ 재무 검토 요청 | 완료 4주 4,319EA, 7/19 재고 6,659EA. 인계 패킷·재무 작업·이력 저장. 승인값 없음 |
| 추가 조달·정보 부족 | 목표 22,000EA·신규 발주 검토·지급일 비움 → ③ 재무 요청 | 권고 1,529EA → MOQ 16,000EA. 과거 단가 기준 추정 201,600,000원. 신규 공급량/현금 유출에 자동 가산 없음. 재무 유출일 확인 작업 생성 |
| 회신 변경 | 기간 추가 20,000EA. 중요 PO 요청 → 미확인 → 16,000EA 확인 → 인계 → 공급 불가 회신 | 미확인 시 공급 0·요청 대기. 확인분은 한 번만 가산. 확인 철회 시 재무 인계 무효화·② 재검토. 공급 불가 의견을 사람이 ③에 전달해도 승인 반려를 자동 생성하지 않음 |
| 기안·자료 변경 | 인계 후 수요 변경 또는 DB 발주 자료 변경 | 기존 SCM 의견·공급 회신 보존, 인계 패킷 무효화, 재검토 및 작업 상태 변경. 원본 CSV 수정 없음 |

같은 명령 재전송은 재실행하지 않는다. 같은 키에 다른 내용은 거절하고, 오래된 버전은 충돌 응답을 반환한다. 미응답 PO 확인 요청을 삭제해서 종료하는 것도 차단했다. 실제 이벤트의 입력·변경 전후·담당자·시각·사유·근거는 [DB 실행 증거](../verification/screen-reviews/02-scm-results.json)에 보관한다.

Chromium에서 시안 섹션 유지·실제 값 표시·권고량 계산 갱신·저장/인계 구분·첨부 파일 패킷·플로우 ③ 표시·새로고침 보존·미확인 회신 후 재검토·390px 화면을 확인했다. [브라우저 증거](../verification/screen-reviews/02-scm-browser.json).

## 실제 작동 / 모의 / 제한

| 구분 | 내용 |
|---|---|
| 실제 작동 | PostgreSQL 검토·회신·작업·파일·버전·이력 저장, 원본 산식·기간 재고 계산, 입력/권한 검증, 사람의 인계 후 단계 갱신 |
| 모의 | 테스트 기안·공급자 회신·부서 답변·담당자 이름. 외부 발주·은행 지급·실제 공급 확약 아님 |
| 별도 ③ 범위 | 재무의 공식 전망·신규 약정 확정·상신. 이번 ②는 그 입력 패킷·작업까지만 책임짐. 작업 폴더에 병행된 ③ 변경은 보존 |
| 남은 한계 | 최신 회신 한 건/기존 PO. 분할입고 여러 일정·복수 조달 대안 최적화는 미구현. 신규 조달안의 가정 입고는 기준 공급량에서 제외 |
| 모델 한계 | 기존/추가 수요 일별 균등 배분. 라이브 피크·물류 처리능력·미래 확정 판매를 보장하지 않음. 현재 기안 단독 검산이며 여러 캠페인의 재고 예약·배정을 확약하지 않음. 검토기간 밖 공급 보장 없음 |
| 운영 경계 | 시연 역할은 실제 계정별 인증이 아님. 온라인 재배포·운영 DB 쓰기·외부 메시지·유료 AI 호출은 하지 않음 |

재무 작업을 재검토로 철회한 경우는 '종료(재검토)', 전제가 바뀌어 유효하지 않은 미응답 SCM 요청은 '종료(전제 변경)'로 구분한다. 답변이 확인되어 완료된 것처럼 표시하지 않는다.

## 변경 파일과 기존 작업 보존

- SCM 계산·검증·작업·패킷: app/scm.py.
- 저장·인계·무효화 연결: app/server.py, app/workflow.py, app/marketing.py, app/domain.py.
- 시안 ② 연결: web/scm.js, web/design.js, web/design.css, web/index.html. 원본 시안·추출된 ② 골격은 보존.
- 검증: tests/test_scm.py, scripts/verify_scm.py, scripts/verify_scm_browser.py. 기존 마케팅 브라우저 검증에서 ②를 미구현으로 보던 조건을 갱신.
- 공유 상세 조회 호환: 병행된 app/performance.py에서 참조 기안이 없는 경우의 None 처리 한 줄 보완. 새 기안을 SCM에서 조회할 때 발생한 오류를 해소했으며 재무 판단 규칙을 바꾸지 않음.
- 이력: 이 문서·02-scm.md·검토 추적표·CHANGELOG·PROTOTYPE 및 실행 증거.

③ 관련 파일이 별도 작업으로 동시에 변경되는 상태를 확인했다. 그 파일을 되돌리거나 이번 ② 결과로 덮어쓰지 않았다. 공유 파일에 두 작업이 섞여 있어 이번 결과는 문서·실행 증거·작업 트리로 남기고, 타 작업을 함께 묶는 커밋은 생성하지 않았다.

## 재현

운영 자료가 없는 별도 로컬 DB에서 migrate·seed 후 서버를 실행한다. 추가 테이블·외부 의존성은 필요하지 않으며 기존 JSONB 검토 건·작업·사건 테이블을 사용한다.

```sh
python -m unittest tests.test_domain tests.test_finance tests.test_marketing tests.test_drafts tests.test_scm -v
W01_TEST_BASE_URL=http://127.0.0.1:8085 python -m scripts.verify_scm
W01_TEST_BASE_URL=http://127.0.0.1:8085 python -m scripts.verify_scm_browser
```

브라우저 검증은 선택 개발 도구인 Playwright/Chromium이 필요하다. DB 시연은 모의 검토 건을 만들고 테스트용 발주 자료를 변경한 뒤 복원하므로 운영 환경에서 실행하지 않는다. 이번 검증의 원본·시안·보호 설정 77개는 작업 전후 SHA-256이 동일하다.

# ④ 승인 여부 결정 · 승인권자 화면 검토

2026-11-10 · **검토 완료 / 사용자 컨펌 대기 / 앱 반영 전**.

③의 완료·반영 기록과 현재 재무 상신 인터페이스를 확인한 뒤 첨부 시안 ④를 대조했다. 시안의 제목 → 결재란 → 5W1H → 추천/근거 → 결정/사유 → 첨부 배치는 유지한다. 독자 UI를 새로 만들지 않는다. [최우선 Rule](../guides/PROJECT_RULES.md).

## 결론과 컨펌 요청 방향

**현재 시안을 그대로 최종 승인 기능으로 연결하면 안 된다.** 캠페인 집행·재고 발주를 하나의 승인으로 묶고 CEO/이사회를 고정하며, 과거 성과를 근거로 반려를 고정 추천하고, 승인하면 무조건 ⑤로 넘어가도록 되어 있다. 기한 경과의 계약 효력도 시스템의 사람 승인과 구분해야 한다.

다음 여섯 방향을 컨펌받아 적용한다.

1. 승인 대상·필요 권한·금액·수량/범위·지급 일정·기안/재무 버전을 분리하고 ③ 상신 그대로 조회한다.
2. ③ 유효 상신·현재 근거·권한을 서버에서 검증한다. 원문이나 조건을 바꾸려면 담당 부서 재검토·재상신으로 돌린다.
3. 승인/반려에 보류·추가 확인과 조건부 승인을 구분한다. 모든 결정에 사람·시각·사유·범위·근거를 남긴다.
4. 승인된 발주만 ⑤ 준비 작업으로 연결한다. 캠페인 승인과 전속계약 결정은 별개이며, 반려·보류 후에도 미해결 확인·계약 통보 작업은 보존한다.
5. 과거 실적·기초/검토안 현금·SCM 공급 의견·대안의 출처와 가정을 표시한다. 반려를 자동 선택하거나 승인만으로 현금 문제가 해결된 것처럼 표시하지 않는다.
6. 승인 기록 추가와 경제적 전제 변경의 해시를 분리하고, 승인 대상별 근거 스냅샷·변경 무효화·중복/동시 처리 방지를 연결한다.

추가 버튼·기록·작업·무효화 규칙은 참가자 내부 통제다. 원본 회사 규정에 이미 있는 상세 절차라고 주장하지 않는다.

## 3. 권한·숫자 교차검증

공식 원본의 승인 권한과 현재 규칙 계산을 비교했다. 아래 일자는 **규정 검산용 가정**이며 실제 승인/지급 일정이 아니다. 현금 시나리오는 보수적 exclude_pay 확정 가정이다.

| 대상 | 가정 유출일 | 권한 계산 |
|---|---|---|
| 캠페인 18,962,703원, 기안 묶음 180,803,272원 | 9/21, 하회구간 밖 | Masil 대표 승인 + 그룹 보고 |
| 같은 캠페인 신규 약정 | 7/27, 하회구간 안 | CEO/이사회 |
| 신규 발주 201,600,000원 | 9/21, 하회구간 밖·추가 하회 미발생 | SCM 전결 |
| 같은 신규 발주 | 8/21, 하회구간 안 | CEO/이사회 |

따라서 한 페이지를 항상 CEO/이사회 승인으로 고정하면 안 된다. 또한 **기존 SPO-0001~0014의 원본 의무는 하회 원인 참고자료**이지 다시 승인해 새 의무를 만드는 대상이 아니다. 기존 발주 변경·새 발주는 별도 요청 범위를 표시한다.

연간 고정 피 28억원 계약은 연액 기준으로 상위 권한에 해당하지만, 유출 일정 미확인을 승인 진행 가능으로 바꾸지 않는다. 캠페인/발주/연간 계약을 한 건의 단순 금액 합산이나 하나의 승인 도장으로 대체하지 않는다.

현금 12.66억원은 다음 조건에서 재현된다.

- 연체채권 유입 제외 / 연체채무 7/1 지급 / 주말 조정 미적용.
- 기초 전망 최저 **1,467,664,440원(14.68억)**.
- **별도 신규 발주 201,600,000원**을 **8/21** 전사 현금 유출에 추가.
- 검토안 최저 **1,266,064,440원(12.66억)**, 첫 해당일 **8/21(8/17 주)**.
- 표본 마케팅 예산은 전사 현금에 추가하지 않음.

이는 특정 제안의 영향 전망이지 이미 승인된 결과가 아니다. 승인 결정 자체로 30억원 약정 하회가 해결되지는 않는다. 원본 약정을 무시하거나 그룹 지원이 확보됐다고 가정하지 않는다.

CMP-0003의 기존 실적 공헌이익 **−30,674,334.9원**, 실질 ROAS 약 **−0.25**, **24/25위**는 ③과 동일 비용/주문 가정에서 재현됐다. 과거 성과의 검산과 이번 계획의 승인 판단은 구분한다. 상세 입력·출력·소스 해시는 [04-approval-evidence.json](../verification/screen-reviews/04-approval-evidence.json).

| 승인 조건과 후속 책임은 무엇인가? | 적용 범위·선행조건·확인 담당자·기한·증빙·재승인 여부 | 조건 문구만으로 지급일/금액/수량을 바꾸지 않음. 경제 조건 변경은 ②/③ 재검토 후 사람 재승인 |
| 결정 후 남는 의무는 무엇인가? | 승인된 발주 준비, 반려/보류 보완, 계약 통보·그룹 보고·미응답 확인 작업 | 승인=집행/외부 통보 완료로 처리하지 않음. 필요한 작업과 실제 증거를 분리 |

**권한 시연 권고:** 현재의 '승인권자' 역할은 유지하되 실제 기록 유형(예: SCM 전결, Masil 대표 승인, 그룹 CEO 승인, 이사회 의결 모의 기록)과 필요한 권한을 명시한다. CEO/이사회 표기만으로 두 주체 모두 실제 결재했다고 표시하지 않는다. 자료에 없는 이사회 정족수·복수 결재 인원·전자서명 효력을 새로 가정하지 않는다.

## 5. 결정·후속 처리안

다음은 원본의 승인권한을 보존하기 위한 **추가 설계/내부 통제**다.

- **승인:** 대상·금액/수량·일정·근거 버전·권한·사유를 고정. 승인된 발주안만 ⑤ 준비 작업으로 넘기며 실제 발주서 전달/지급/계약 통보는 별도 행위다.
- **조건부 승인:** 조건·담당자·기한·증빙을 작업으로 생성. 조건 이행 확인 후 재검토·사람 재승인 전에는 실행 허용으로 취급하지 않는다. 기존 프로토타입의 조건부 승인 경계를 유지한다.
- **보류·추가 확인:** 질문·보완 담당자·필요 증빙·기한을 저장하고 ④ 결정 대기를 유지. 침묵을 승인이나 반려로 바꾸지 않는다.
- **반려:** 대상별 이유와 마케팅/SCM/재무 보완 작업 생성. 승인된 것으로 기록하지 않으며, 신규 제안의 반려로 기존 PO 지급 의무를 자동 취소하지 않는다.

같은 상신 안에 여러 대상이 있으면 각 대상의 결정과 의존 관계를 기록한다. 일부 결정/조건 미해소 상태는 ④에 남긴다. 캠페인이 반려됐는데 그 증가 수요만을 근거로 한 발주를 그대로 실행하지 않는다. 원래의 기초 재고 보충으로 독립 진행하려면 그 근거·수량·기간을 다시 확인하고 필요하면 ②/③에서 재검토한다.

캠페인만 승인됐고 발주 대상이 없으면 '발주 대상 없음'을 명시하고 마케팅 승인 결과 기록 작업을 만든다. 없는 발주를 ⑤/⑥ 완료로 꾸미지 않는다. 전체 흐름의 예외 경로 상세는 전체 진행 화면 검토에서 확인하되, 이번 ④는 허용된 대상·다음 담당자·미해결 작업을 실제 저장해야 한다.

원본의 'Masil 대표 승인 + 그룹 보고'는 보고 의무를 남긴다. 대표 승인만으로 그룹 보고까지 자동 완료시키지 않는다. 원본에 보고의 정확한 선후 시점은 없으므로 '보고 완료 전 집행 절대 금지' 같은 별도 규칙을 원본 규정으로 만들지 않는다.

**기한 경과:** 가상기업 기준일과 실제 기록 시각을 구분한다. 계약 자동 확정/갱신은 원본 조건에 따른 외부 계약 효과다. 시스템 승인 기록이 자동 생성되는 것은 아니다. 기한이 지나면 통보 이행·효력·대응 근거를 확인하고 늦은 결정을 소급 승인처럼 표시하지 않는다. 캠페인을 반려해도 INF-001 연간계약 통보 작업은 종료하지 않는다.

## 6. ③–④ 연결에서 확인한 기술적 필수 보완

현재 app/finance_review.py의 basis는 finance_review·routing을 제외한 case 전체를 포함한다. 읽기 전용 로컬 객체로 검산한 결과, 경제적 전제를 바꾸지 않고 approval 필드만 추가해도 재무 valid가 **True → False**로 바뀌었다. 이는 ③의 기존 상신 시점 검증을 부정하는 것이 아니라 **④ 결정 기록을 연결할 때 새로 발생할 문제**다.

④ 구현 시 기안·수요·SCM 검토·약정 조건·자료·재무 시나리오 등 **경제적 전제**와 승인/업무 상태/열람 기록을 구분한다. 승인 기록이 스스로 자기 근거를 무효화하지 않아야 한다. 반대로 금액·수량·지급일·공급 회신·재무 시나리오가 바뀌면 관련 승인은 재검토 대상으로 표시하고 이전 결정 이력은 보존한다.

현재 상신 패킷에 있는 대상별 결정·금액·지급 일정·현금/성과 가정과 승인 스냅샷을 연결해야 한다. 기존 단일 SKU 승인 API를 새 다중 대상 캠페인 승인에 그대로 사용하거나, 상태 값 하나를 승인으로 바꾸는 식으로 우회하지 않는다.

## 7. 컨펌 후 검증할 조건

1. 현재 유효한 ③ 상신만 승인 대상으로 조회. 기안/상신 미존재·근거 변경·지급일/금액 미확인·중요 질문 미해결 상태는 명확히 표시/차단.
2. 캠페인/발주/계약의 대상별 권한과 금액/수량·전체 지급 일정 고정. 잘못된 권한·다른 역할·대상 누락/중복·클라이언트 승인값 주입·구버전/중복 결정 차단.
3. 승인 기록을 추가해도 동일 경제 전제의 재무 근거는 유효. 실제 전제 변경은 관련 승인과 작업을 재검토로 전환. 과거 결정은 보존.
4. 승인/조건부/보류/반려별 결정자·시각·가상 적용일·사유·권한·근거·대상 버전을 DB에 저장. 모의 승인임을 실제 기업 승인과 구분.
5. 조건부 승인·미확인/반려 대상에서 발주/지급/계약 확정을 자동 실행하지 않음. 승인된 관련 발주만 ⑤ 작업 생성.
6. 캠페인 반려로 기존 PO·기존 부채·연간 전속계약·통보 의무가 자동 취소되지 않음. 기한 경과는 사람 승인으로 둔갑하지 않음.
7. 부분 결정·서로 다른 권한·분할 지급·캠페인과 발주의 의존 관계·조건 이행 후 재승인·재무 시나리오 변경을 모의 시나리오로 검증.
8. 첨부 시안의 ④ 섹션과 단계 플로우 유지. 실제 서버 저장 후에만 '결정 기록됨' 표시. 새로고침 보존·오류/빈 상태·모바일·기존 단일 SKU 기록 호환 확인.

이번은 검토·계산 근거 기록만 수행했다. **앱 코드·④ 실제 결정 기능·원본·시안·DB는 변경하지 않았다.** ④ 아니오 세부 화면·⑤ 발주서 페이지의 재설계는 이번 컨펌에 포함하지 않는다.
